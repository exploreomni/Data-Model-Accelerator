# Synthetic Power BI migration: subscription billing

This authored PBIP/TMSL/PBIR project reuses the invented raw billing records and CSV adjustments from the Tableau/Hex pilots to isolate Power BI semantics. It is not a customer export. Namespace DMA_POWERBI, account DMA_POWERBI_SYNTHETIC, RAW schema, snapshot 2026-03-02T00:00:00Z. Metadata exports are synthetic and must bind the exact source account, database, schema, tables and required columns. ADJUSTMENTS is a proposed governed landing of the supplied CSV, not evidence of existing ingestion.

## Shared warehouse contract

Raw INVOICE_CDC, PAYMENT_CDC, CUSTOMER_HISTORY and CSV ADJUSTMENTS retain exact uppercase input columns. Amounts are integer USD cents. Highest SEQUENCE wins at tenant/business-key grain BEFORE tombstone filtering. Identical versions are idempotent; conflicting same-sequence versions, null keys, missing references, overlapping history and duplicate/orphan adjustments fail. Customer history binds by invoice date in [VALID_FROM,VALID_TO), null end open. Payments deduplicate at tenant/payment, then aggregate at tenant/invoice before joining. Missing adjustment rows mean zero; missing file fails. NET_CENTS=AMOUNT_CENTS+ADJUSTMENT_CENTS, OUTSTANDING_CENTS=NET_CENTS-PAID_CENTS; preserve negative net and overpayment. Gold retains all current nondeleted statuses at tenant/invoice grain. Customer dimension grain is tenant/customer/valid-from. Fixture keys tenant|invoice and tenant|customer|valid-from exclude pipes in components; production requires an agreed collision-safe encoding. Raw date columns are physically VARCHAR, typed in silver with explicit local DATE adaptation.

## Source project and placement

One authored PBIP project points to a local report and one TMSL model.bim semantic model. Three tables: Invoices, Customers (effective-dated history), Scenario (disconnected values 1 and 2). Invoices and Customers each have an Import M partition with a Snowflake native SQL query. Invoices SQL performs CDC, payment preaggregation, temporal binding and adjustment join. Subsequent M steps calculate Net Cents using a zero replacement for null adjustment, and Invoice Month using Date.StartOfMonth. An Invoices DAX calculated column computes Outstanding Cents. These reusable rules move upstream. A single active many-to-one, single-direction relationship maps Invoices Customer History Key to Customers Customer History Key; propagation uses that exact composite key. Missing, inactive, bidirectional, many-to-many or ambiguous relationships are unsupported for replay and must fail visibly. Scenario is deliberately disconnected.

Native source column names: Invoices[Tenant ID], [Invoice ID], [Customer ID], [Invoice Date], [Invoice Month], [Status], [Amount Cents], [Adjustment Cents], [Paid Cents], [Net Cents], [Outstanding Cents], [Customer History Key], [Invoice Key]; Customers[Tenant ID], [Customer ID], [Segment], [Valid From], [Valid To], [Customer History Key]; Scenario[Multiplier]. Column sourceColumn mappings preserve uppercase SQL/M names. The source facts need not contain Segment: it is read through the relationship.

Source measures: Revenue Cents=SUM(Invoices[Net Cents]); Paid Cents=SUM(Invoices[Paid Cents]); Outstanding Cents=SUM(Invoices[Outstanding Cents]); Payment Rate=DIVIDE([Paid Cents],[Revenue Cents]); All Segment Revenue Cents=CALCULATE([Revenue Cents],REMOVEFILTERS(Customers[Segment])); Share All Segments=DIVIDE([Revenue Cents],[All Segment Revenue Cents]); Posted Revenue Cents=CALCULATE([Revenue Cents],Invoices[Status]="posted"); Posted Intersection Cents=CALCULATE([Revenue Cents],KEEPFILTERS(Invoices[Status]="posted")); Scenario Revenue Cents=[Revenue Cents]*SELECTEDVALUE(Scenario[Multiplier],1). SUM over no values and DIVIDE with zero/blank denominator return BLANK (JSON null). No averaging of ratios or summing visual subtotals to produce totals. All Segment Revenue removes only ordinary segment filters; it preserves date, status, grouping month and security.

## Report and security contexts

Three native PBIR visuals: Revenue Trend, Segment Share, KPI Totals. Report defaults: tenant A role, start_date 2026-01-01 inclusive, end_date 2026-03-01 exclusive, segment ALL (no segment predicate), status posted, multipliers [1]. Two authored roles TenantA and TenantB restrict BOTH Invoices and Customers to tenant A/B, respectively. Local persona must match the selected role. Missing/unknown role or tenant, mismatched persona, denied authorization, malformed/reversed dates, unknown status, unsupported multiplier selections fail. These are modeled-role tests, not service role membership or actual RLS enforcement. Security restrictions are independent of ordinary filter context and cannot be removed by a measure.

Runtime parameters: tenant A/B; start_date/end_date ISO dates; segment any string with ALL meaning no filter; status posted/draft; multipliers a unique subset of [1,2] (empty/multiple values use SELECTEDVALUE alternate 1). Defaults must originate in native report evidence where applicable; tenant-role/persona context is a local test harness binding. No hidden filters, bookmarks, interactions or measures may be silently discarded. Unsupported native behavior is an explicit coverage gap.

Revenue Trend groups month then historical segment and outputs month, segment, revenue_cents, paid_cents, outstanding_cents, payment_rate, scenario_revenue_cents. Segment Share groups month then historical segment and outputs month, segment, revenue_cents, all_segment_revenue_cents, share_all_segments. These grouped visuals enumerate keys with visible selected fact rows; no show-items-with-no-data or densification claimed. KPI Totals has no grouping and always returns ONE row with revenue_cents, paid_cents, outstanding_cents, payment_rate, all_segment_revenue_cents, share_all_segments, posted_revenue_cents, posted_intersection_cents, scenario_revenue_cents. Empty selected populations return zero grouped rows and a one-row KPI result of BLANKs except any CALCULATE measure whose changed context has qualifying rows. A draft status filter makes Posted Revenue replace that filter while Posted Intersection preserves the conflicting restriction and returns BLANK. A segment selection makes the all-segment denominator include other segments, unlike a filtered visual share. Totals are recomputed from their own context.
