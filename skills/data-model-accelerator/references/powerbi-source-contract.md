# Power BI source contract

Verified against primary Microsoft sources on 2026-09-11. This is an authored synthetic PBIP/TMSL/enhanced-PBIR case and a bounded static parser. It is not a customer export, a general Power BI converter, or evidence of native application acceptance.

## Native formats and validation boundary

Microsoft documents `.pbip` as a report-folder pointer. `definition.pbir` binds the report to its semantic model; this fixture uses a confined local `byPath`. `definition.pbism` version 1.0 selects TMSL `model.bim`, a database object containing its model. The report uses enhanced PBIR's separate report/page/visual files. Microsoft currently labels **Power BI Desktop projects as preview**. [PBIP overview](https://learn.microsoft.com/en-us/power-bi/developer/projects/projects-overview), [semantic-model folder](https://learn.microsoft.com/en-us/power-bi/developer/projects/projects-dataset), [report folder](https://learn.microsoft.com/en-us/power-bi/developer/projects/projects-report).

The unmodified [Microsoft schema repository](https://github.com/microsoft/json-schemas/tree/f36df424cb31e0634757d015902688c65bf5f8e5) is pinned at commit `f36df424cb31e0634757d015902688c65bf5f8e5`. `scripts/schemas/powerbi/` contains its 12-file dependency closure, license and per-file SHA-256 provenance. Root contracts are PBIP 1.0.0, PBISM 1.0.0, report-definition properties 2.0.0, report 3.3.0, page 2.1.0, visual container 2.9.0, pages metadata 1.1.0 and version metadata 1.0.0. All ten authored project/report JSON files pass those official schemas using an offline registry. The parser checks pinned hashes and never fetches a source-supplied schema URL.

This validation excludes `model.bim`'s TOM semantics, M and DAX execution, connection authentication, refresh, folding and visual rendering. The model receives explicit local structure/reference checks; no handmade schema is presented as Microsoft certification. Native Desktop, TOM and Analysis Services are unavailable in this run. A schema-valid visual can still require native opening and behavioral verification.

## Fixture identity and source grammar

`examples/powerbi-omni-e2e/input/repo/Billing.pbip` points to `Billing.Report`. Its `definition.pbir` references `../Billing.SemanticModel`. The semantic model's database name is `DMA Power BI Billing`, model name `Model`, with Invoices, Customers and Scenario tables. Names and 32 lineage tags are authored fixture identifiers, not server-issued identity evidence. The single page is `ReportSectionBilling`; native visual IDs are `RevenueTrend`, `SegmentShare` and `KPITotals`. Their displayed titles are native title expressions. Each is a `tableEx` visual with explicit ordered projections; chart appearance parity is outside this pilot.

Invoices and Customers each have one Import M partition. `Value.NativeQuery` uses a literal `Snowflake.Databases` database selection and literal SQL, with `EnableFolding=true`. Static extraction records that option; it does not establish actual folding. SQL normalizes CDC, preaggregates payments and binds effective-dated customers. Invoices M then adds `NET_CENTS` with a null-adjustment replacement and `INVOICE_MONTH` with `Date.StartOfMonth`; DAX calculates Outstanding Cents. Scenario uses `#table` containing integer multipliers 1 and 2. [Native-query folding](https://learn.microsoft.com/en-us/power-query/native-query-folding), [Date.StartOfMonth](https://learn.microsoft.com/en-us/powerquery-m/date-startofmonth).

Nine measures retain the scenario's names and formulas. They are homed on Scenario because Invoices already has Paid Cents and Outstanding Cents columns. Microsoft prohibits same-table column/measure name collisions and describes measure home-table association as cosmetic. Fully qualified column references distinguish the row fields from measures. [DAX naming and references](https://learn.microsoft.com/en-us/dax/best-practices/dax-column-measure-references).

The single active relationship is `Invoices_Customers_History`, from the fact's Customer History Key to the customer's same key, many-to-one and single-direction. TenantA/TenantB filter both tables; role names do not prove service membership or enforcement. [Relationship contract](https://learn.microsoft.com/en-us/analysis-services/tmsl/relationships-object-tmsl?view=sql-analysis-services-2025), [roles](https://learn.microsoft.com/en-us/analysis-services/tmsl/roles-object-tmsl?view=sql-analysis-services-2025).

## Extraction API and evidence

`scripts/powerbi_source.py` exposes `inspect_repo(repo)`. The graph retains the complete database object in `model`, native objects, source paths, current asset hashes, columns/sourceColumn mappings, M/DAX text, declared connections, SQL reads/CTEs/joins, relationships, roles and scoped dependency edges. `visuals` preserves ordered `{kind, table, property, queryRef}` projections plus title, position, native JSON and filters. Normalized filters carry target, operator, literal values, scope and original definition.

`report_defaults` comes from five native report filters: ReportingStart includes 2026-01-01; ReportingEnd excludes 2026-03-01; StatusSelection is posted; MultiplierSelection is 1; the explicit SegmentSelection field card has no predicate, represented as ALL. Separate `report_default_evidence` records each native origin. Tenant/role/persona selection remains external harness context.

The baseline contains 12 assets, three tables, 20 columns, nine measures, three partitions, one relationship, two roles, one page, three visuals, five filters and 48 edges. All required native files are read; CSV is inventoried separately. SQL physical references and full column inventories do not establish expression-level column lineage. ADJUSTMENTS is a proposed governed landing of that CSV, not discovered ingestion.

## Failure and semantic boundaries

Duplicate JSON keys, case-colliding assets, duplicate native IDs, unresolved fields, stale query references, mismatched filter targets, unsafe relative references and source symlinks fail visibly. Limits are 200 files, 2 MB per file and 10 MB total. PBIX/TMDL, remote models, pending changes, orphan assets, bookmarks, hidden/unsupported visuals, interactions, page/visual filters, densification and unsupported relationship modes produce gaps; they are not silently discarded. Missing whole visuals cannot be proved absent from repository evidence alone: a separately captured expected inventory is needed.

M recognition and DAX references are static evidence, not full language parsing. Unbound/dynamic native-query sources fail; additional language semantics require the separate reviewed interpreter. `CALCULATE` replaces a filter on the same column; `KEEPFILTERS` intersects it. `REMOVEFILTERS(Customers[Segment])` removes that ordinary segment restriction, not unrelated date/status context. `SELECTEDVALUE` uses its alternate for zero/multiple values; `DIVIDE` has an explicit blank/zero-denominator contract. These distinctions must survive replay rather than being flattened into precomputed visual totals. [CALCULATE](https://learn.microsoft.com/en-us/dax/calculate-function-dax), [KEEPFILTERS](https://learn.microsoft.com/en-us/dax/keepfilters-function-dax), [REMOVEFILTERS](https://learn.microsoft.com/en-us/dax/removefilters-function-dax), [SELECTEDVALUE](https://learn.microsoft.com/en-us/dax/selectedvalue-function-dax), [DIVIDE](https://learn.microsoft.com/en-us/dax/divide-function-dax).

`static_coverage_complete` means only that this bounded inventory has no static errors. Two explicit review gaps retain the native-runtime and full-language limitations. The canonical source snapshot hashes the sorted current asset list; it does not establish export completeness, security acceptance or deployment readiness.
