# Reviewed AI context and answer evaluation

`scripts/omni_ai_context.py` creates a private, deterministic context bundle from
explicit reviewed definitions and their gold model dependencies. It also compares
imported structured answers against a frozen evaluation suite. Neither operation
calls an AI service, updates Omni, authenticates a reviewer, or grants access.

## What the builder checks

The builder requires all five exact input pins: dictionary, source evidence,
candidate model files, model context, and disclosure policy. The review record
also binds the complete specification. Hashes establish integrity against the
supplied inputs; they do not prove who approved them or whether the warehouse
contains the declared data.

The dictionary must be version 2 with privacy extension 1. Every referenced
dictionary model must explicitly have `layer: gold`; the specification must also
identify its binding as gold. A schema name or a `mart_` prefix is insufficient.
Each column needs nonempty catalogue source references matching the candidate's
catalogue pin. Column names and physical namespaces must match exactly.

The candidate must pass the bounded [Omni static contract](omni-static-contract.md).
Field definitions are pinned individually. The builder follows semantic SQL
references, physical columns, distinct measure key expressions, and order-by
field dependencies. Missing or duplicate dependency mappings block generation.
A row count conservatively retains every physical column in its bound view;
aggregation does not automatically remove a privacy classification.

Every definition and every contributing dictionary column must pass the actual
`ai_context` destination in the [disclosure policy](sensitive-data.md). Approval
for warehouse comments or another destination is insufficient. Unknown,
restricted, or otherwise denied content is withheld according to that policy.
Diagnostics contain indexes and fixed reason codes, not withheld identifiers,
SQL, descriptions, source values, or business statements. The bounded content
scanner checks the exact projected JSON and Markdown. It is not universal DLP.

An approved definition needs a nonempty review reference and pinned source
evidence. If a mapped dictionary meaning is still unapproved, the projection
replaces the claim with a review question. Unresolved definitions contain only a
question, never an approved statement. Source values and source pointer paths are
not copied into the output; their evidence hashes are retained.

## Python interfaces

```python
pins = input_pins(
    dictionary=dictionary, source=source, model_files=model_files,
    model_context=model_context, disclosure_policy=policy,
)
result = build_context(
    spec, dictionary=dictionary, source=source, model_files=model_files,
    model_context=model_context, disclosure_policy=policy,
)
write_context(result, new_output_directory)
report = evaluate_answers(suite, observations, result['context'])
```

`build_context` returns `context`, `markdown`, and `report`. Invalid or stale
inputs raise `ContextError` with a fixed value-free code. A structurally valid
partial projection has report status `incomplete`, including when every
definition is withheld. `complete` means the supplied records have no remaining
questions or withholding; it is not native deployment or business acceptance.

`verify_context(context)` validates exact structure, input and field pins, gold
lineage records, definition source hashes, coverage, and content integrity.
It is an integrity check, not proof that an imported context was generated by a
trusted process. Resealing arbitrary inputs does not authenticate their authors.

## Specification shape

The specification uses `schema_version: 1`, `kind: omni_ai_context_spec`, and:

| Property | Required content |
| --- | --- |
| `pins` | The exact five SHA-256 values returned by `input_pins` |
| `bindings` | Map of fully qualified semantic fields to `layer`, `field_sha256`, and complete physical `columns` |
| `definitions` | Distinct approved definitions or unresolved questions |
| `review` | `status: approved`, a review `reference`, and `sha256` of the specification without `review` |

Each binding column is an exact object with `view`, `column`, `model_id`,
`column_id`, and `namespace`. The namespace uses the selected warehouse's
canonical structure from the model context. Each binding's `field_sha256` is the
canonical hash of the resolved native dimension or measure definition.

Each definition has exactly:

```json
{
  "id": "net_amount",
  "status": "approved",
  "statement": "Net amount after recorded adjustments.",
  "question": null,
  "fields": ["shipments.net_total"],
  "source_refs": [{"pointer": "/definitions/net_amount", "sha256": "<canonical source value hash>"}],
  "privacy": "<complete privacy classification object>",
  "review_reference": "<review evidence reference>"
}
```

The example's placeholders must be replaced with real contract objects and
hashes. For an unresolved record, set `status: unresolved`, `statement: null`,
`review_reference: null`, and provide a nonempty `question`. Do not label an
inferred business meaning approved merely because its SQL is valid. Source
pointers bind evidence; this module does not judge whether that evidence supports
the human-authored statement.

Cross-view `extends`, constant-only expressions, native dynamic templates, raw
HTML, and URL-bearing prose need separate review in this bounded projection.
The builder blocks or withholds those cases rather than guessing. This is a
supported-subset boundary, not a claim that Omni universally prohibits them.

## Frozen evaluation contract

An `omni_ai_evaluation_suite` uses schema version 1 and contains the exact
`context_sha256`, a `personas` mapping, `cases`, and a review record binding the
suite without its `review` property. Each persona declares `allowed_fields` and
`available_attributes`; these are test declarations, not observed permission
results or real attribute values.

Each case supplies `id`, `question`, `persona_id`, and `expected`:

```json
{
  "decision": "answer",
  "allowed_fields": ["shipments.net_total"],
  "required_fields": ["shipments.net_total"],
  "definition_ids": ["net_amount"],
  "clarification_ids": [],
  "required_attributes": ["region"]
}
```

Use `refuse` for prohibited disclosure or unavailable required attributes, and
`clarify` for an unresolved definition. Non-answer expectations contain no
allowed or required fields and no approved definition claims. Clarification
identifies only known unresolved question IDs. A case cannot expect an answer
that needs an unavailable attribute or an unapproved definition.

An `omni_ai_observations` object uses schema version 1, the complete reviewed
`suite_sha256`, and exactly one answer per case. Each answer has:

```json
{
  "case_id": "net_amount_question",
  "persona_id": "analyst",
  "question_sha256": "<canonical question hash>",
  "context_sha256": "<context hash>",
  "decision": "answer",
  "fields": ["shipments.net_total"],
  "claims": [{"definition_id": "net_amount", "statement_sha256": "<approved statement hash>"}],
  "clarification_ids": [],
  "attributes_used": ["region"]
}
```

The comparator rejects omitted or duplicate cases, changed questions or
personas, extra fields, fabricated definitions, changed statement hashes,
unavailable attributes, and answers where refusal or clarification was required.
It does not grade a prompt by searching for reassuring words. Free-form answer
prose is not accepted as proof of correctness. A structured pass establishes
only agreement with the supplied frozen contract; it does not establish whether
an AI actually produced that answer, whether its narrative was true, or whether
access controls worked for a live user.

## Private local commands

```bash
python skills/data-model-accelerator/scripts/omni_ai_context.py build \
  --spec /private/path/spec.json \
  --dictionary /private/path/dictionary.json \
  --source /private/path/source-evidence.json \
  --model-files /private/path/model-files.json \
  --model-context /private/path/model-context.json \
  --policy /private/path/disclosure-policy.json \
  --output /private/path/new-context-bundle

python skills/data-model-accelerator/scripts/omni_ai_context.py evaluate \
  --suite /private/path/suite.json \
  --observations /private/path/observations.json \
  --context /private/path/new-context-bundle/AI_CONTEXT.json \
  --output /private/path/new-evaluation-report.json
```

The build command requires the pinned YAML and SQL parsing runtime. Model files
are a JSON map of candidate filenames to file text. The output directory must be
new and its parent must already exist without symlink traversal. It contains
only `AI_CONTEXT.json`, `AI_CONTEXT.md`, and `BUILD_REPORT.json`, with private
directory/file modes `0700`/`0600`. A partial write is cleaned up. Existing output
is never overwritten. A build may exit successfully with an `incomplete`
candidate; inspect the report. Evaluation exits successfully only for a local
structured pass. Console output is limited to fixed status and assurance flags.

## Native adoption and remaining evidence

Omni supports free-text AI context at both [model level](https://docs.omni.co/modeling/models/ai-context)
and [topic level](https://docs.omni.co/modeling/topics/parameters/ai-context).
The documented native context also supports user-attribute and constant
templates. This portable builder deliberately does not execute or author those
dynamic paths. Omni's model context patch mechanism is server-managed; do not
hand-author `ai_context_patch` or overwrite existing curated context blindly.

Review this bundle against the existing model/topic context, merge through the
approved native workflow, then test actual questions in the intended tenant with
the actual personas. Keep the resulting native context, model revision, policy,
principal, attributes, and observation provenance pinned. Follow the official
[AI answer-quality guidance](https://docs.omni.co/guides/ai/improve-ai-answer-quality)
when curating definitions and evaluating responses.

All generated contexts explicitly retain `native_verified: false`,
`review_authority_authenticated: false`, and
`access_enforcement_verified: false`. Evaluation reports retain
`live_ai_authenticated: false` and `natural_language_answer_verified: false`.
Local generation and imported evidence cannot upgrade those claims. Actual
warehouse policy enforcement, tenant AI behavior, business review, and migration
acceptance remain separate evidence lanes.
