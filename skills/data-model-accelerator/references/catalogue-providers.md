# Warehouse catalogue providers

Primary documentation checked **2026-09-09**. The accompanying SQL files are reviewed starter templates, **not live-validated collectors or universally executable scripts**. Each labeled statement is independent and SELECT-only; no statement scans business rows, installs objects, repairs metadata, or changes permissions. Execute only selected statements under the engagement's authorized metadata scope.

## Collection contract

Replace `__DATABASE__`, `__CATALOG__`, `__PROJECT_ID__`, `__DATASET__`, `__SCHEMA__`, and `__REGION__` explicitly. Identifiers and string literals have different escaping rules: use trusted allowlisted values and provider-correct quoting, never raw concatenation of repository text. SQL identifiers cannot generally be supplied as ordinary value parameters. Keep qualifiers even when the connection has defaults. Record all substitutions in the collection manifest.

Preserve provider/account or project, endpoint/workspace/metastore where applicable, region, database/catalog, schema/dataset, object name, native object ID when exposed, and exact identifier case. Record principal, active role context, query/job IDs, collection start/end, query text/hash, permissions/visibility assumptions, requested scope, returned counts, pagination completion, and errors per statement. Multiple statements do not establish an atomic metadata snapshot. Avoid widening credentials merely to achieve a green completeness flag.

Capture raw provider results before canonical normalization. Differentiate **absent**, **not collected**, **not visible**, **unsupported**, and **unknown**. A successful empty result is complete only for its verified query scope and visibility. Retain partial results when optional views fail. Catalogues prove declared structure; constraints are not independent uniqueness/fanout tests, metadata row counts are not profiles, and modification timestamps do not prove business freshness. Never infer replication source, delete handling, CDC ordering, history, or completeness from naming conventions; obtain connector configuration and operational evidence separately.

## Snowflake

Use [snowflake.sql](../examples/catalogue-queries/snowflake.sql) once per approved database/schema. Information Schema lives in every database. Its object views expose current-role-visible objects and do not honor `MANAGE GRANTS` the same way as `SHOW`; absence cannot establish account-wide nonexistence. Start with object types, columns, comments, view text, and declared constraints. A missing/hidden definition remains unknown. [Information Schema](https://docs.snowflake.com/en/sql-reference/info-schema), [TABLES visibility](https://docs.snowflake.com/en/sql-reference/info-schema/tables)

`COLUMNS` supplies type/precision/nullability/default/comment and `DTD_IDENTIFIER`; `FIELDS`/`ELEMENT_TYPES` can describe declared structured OBJECT/MAP/ARRAY types. These do not discover arbitrary contents of VARIANT values. Preserve type identifiers for optional nested-type expansion. [COLUMNS](https://docs.snowflake.com/en/sql-reference/info-schema/columns), [Structured fields](https://docs.snowflake.com/en/sql-reference/info-schema/fields)

Standard-table primary/foreign/unique constraints differ from enforced hybrid-table constraints. Preserve `ENFORCED`, table kind, and the original declaration; verify business grain independently. Information Schema constraint names alone do not supply ordered key columns. An optional scoped `SHOW PRIMARY KEYS`/`SHOW IMPORTED KEYS` or DDL export needs a separate metadata step; it is intentionally outside these SELECT templates. [Constraint behavior](https://docs.snowflake.com/en/sql-reference/constraints-overview)

Optional account-level exports can add internal IDs, dropped objects, dependencies, policy attachments, grants, loading/task histories, and clone/storage context. `ACCOUNT_USAGE` has **per-view latency**; do not apply one universal freshness bound or mix historical and current rows without timestamps. `TABLE_STORAGE_METRICS` clone groups indicate storage relationships, not complete replication lineage. Capture each optional view's availability, edition/role requirements, and latency. [Account Usage catalogue](https://docs.snowflake.com/en/sql-reference/account-usage), [Policy references](https://docs.snowflake.com/en/sql-reference/account-usage/policy_references), [Storage and clone groups](https://docs.snowflake.com/en/sql-reference/account-usage/table_storage_metrics)

`SHOW TABLES` supports name-cursor pagination with a 10,000-row limit; an unbounded oversized result errors. Scope carefully and reconcile pages. Information Schema queries need selective filters; SQL API results have partitions that must all be fetched. A truncated UI result is incomplete. [SHOW TABLES](https://docs.snowflake.com/en/sql-reference/sql/show-tables), [SQL API partitions](https://docs.snowflake.com/en/developer-guide/sql-api/handling-responses)

## Databricks Unity Catalog

Use [databricks.sql](../examples/catalogue-queries/databricks.sql) per approved catalog/schema. Information Schema is **Unity Catalog only**: catalog-local views cover that catalog, while `system.information_schema` spans accessible catalogs and excludes `hive_metastore`. Visibility is privilege-aware and requires relevant access. Preserve workspace/metastore scope outside SQL where not exposed. Most identifier values are normalized lowercase, except column/tag names; do not overwrite original names from other evidence. Some metadata changes require synchronization; report stale evidence rather than running `REPAIR TABLE` during collection. `LIMIT` does not provide supported pushdown; use selective predicates. [Scope, permissions, and limitations](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-information-schema)

Keep `FULL_DATA_TYPE` alongside `DATA_TYPE` for STRUCT/ARRAY/MAP shape. Some COLUMNS fields, including `COLUMN_DEFAULT`, are reserved and always NULL: NULL is not proof no default exists. Optional `DESCRIBE TABLE EXTENDED ... AS JSON` provides richer nested type/nullability/comment/default metadata; its documentation requires Databricks Runtime 16.2 or above and a compatible SQL surface. This non-SELECT command is outside the starter file. [COLUMNS](https://docs.databricks.com/aws/en/sql/language-manual/information-schema/columns), [Structured metadata export](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-aux-describe-table)

TABLES distinguishes external/managed relations and documented shallow-clone types. View definitions are NULL for nonowners. Optional key-constraint statements are labeled **Public Preview** according to the linked AWS documentation, and report declarations rather than proof. Recheck the selected cloud/runtime's status. [TABLES](https://docs.databricks.com/aws/en/sql/language-manual/information-schema/tables), [VIEWS](https://docs.databricks.com/aws/en/sql/language-manual/information-schema/views), [TABLE_CONSTRAINTS](https://docs.databricks.com/aws/en/sql/language-manual/information-schema/table_constraints)

For governance, optionally collect visible privilege, tag, row-filter, column-mask, and ABAC-definition views from the Information Schema catalogue. Missing rows cannot certify no policy applies. Authorized system lineage, query/job/pipeline history, and table history can supplement operational evidence; lineage tables capture only a subset of events. Statement Execution API row/byte limits and result chunks must be reconciled; `truncated=true` prevents completeness. [Lineage limitations](https://docs.databricks.com/aws/en/admin/system-tables/lineage), [Statement results](https://docs.databricks.com/api/statement-execution/v1/execute-statement)

## Google Cloud BigQuery

Use [bigquery.sql](../examples/catalogue-queries/bigquery.sql) per approved project/dataset and region. Regional inventory needs a matching query execution location; regions are not hierarchical, so `region-us` does not include every `us-*` location. Enumerate approved locations separately. Metadata access and query-job permissions are distinct: COLUMNS needs `bigquery.tables.get/list`; SCHEMATA needs project-level `bigquery.datasets.get`. Follow each optional view's documented permissions rather than assuming one role exposes everything. [Scope and location](https://cloud.google.com/bigquery/docs/information-schema-intro), [SCHEMATA](https://cloud.google.com/bigquery/docs/information-schema-datasets-schemata)

TABLES provides object type, DDL, and base identity/snapshot time for clones and snapshots. Collect COLUMNS and COLUMN_FIELD_PATHS separately; retain nested field paths, descriptions, types, and policy tags. Field-path metadata is not complete nested nullability/mode evidence: an optional Tables API schema export preserves recursive fields and `NULLABLE`/`REQUIRED`/`REPEATED` modes. Do not infer a nested array's row grain. [TABLES](https://cloud.google.com/bigquery/docs/information-schema-tables), [COLUMNS](https://cloud.google.com/bigquery/docs/information-schema-columns), [Nested fields](https://cloud.google.com/bigquery/docs/information-schema-column-field-paths), [Table resource](https://cloud.google.com/bigquery/docs/reference/rest/v2/tables)

TABLE_OPTIONS supplements external-source configuration, descriptions, partition settings, labels, and other properties; treat URLs and definitions as confidential metadata. Declared primary/foreign keys are not enforced. Optional IAM/row-access/data-policy exports must establish policy definitions and identity bindings; policy tags alone cannot prove effective access. The documented COLUMNS `data_policies` field is **Preview** and is omitted from baseline templates. [Table options](https://cloud.google.com/bigquery/docs/information-schema-table-options), [Constraints](https://cloud.google.com/bigquery/docs/information-schema-table-constraints), [Row-access policy listing](https://cloud.google.com/bigquery/docs/reference/rest/v2/rowAccessPolicies/list), [Table IAM policy](https://cloud.google.com/bigquery/docs/reference/rest/v2/tables/getIamPolicy)

Optional JOBS, transfer-run, audit, PARTITIONS, and TABLE_STORAGE exports provide bounded operational or metadata statistics, not a source connector's CDC contract or measured profiles. Inspect each source's region, retention, visibility, and collection scope. For query results, require successful completion, exhaust `pageToken`, and reconcile `totalRows`; a displayed page is not the full result. [Information Schema catalogue](https://cloud.google.com/bigquery/docs/information-schema-intro), [Result pagination](https://cloud.google.com/bigquery/docs/reference/rest/v2/jobs/getQueryResults)

## Amazon Redshift

The added Redshift and ClickHouse templates were checked against primary metadata documentation on **2026-09-24**. MotherDuck uses current official DuckDB metadata contracts and MotherDuck connection guidance; live cloud compatibility remains unverified. [redshift.sql](../examples/catalogue-queries/redshift.sql) records observed SQL session context and scoped `SVV_ALL_TABLES`/`SVV_ALL_COLUMNS` metadata. Preserve database/schema/name, region, cluster or workgroup, IAM and database identities, and statement IDs. These views have principal-dependent visibility; AWS now recommends `SHOW TABLES`/`SHOW COLUMNS` for discovery across local, datashare and external contexts. Those separately authorized commands are outside the SELECT-only template. Retain missing coverage rather than implying the template inventories every Redshift surface. [Tables](https://docs.aws.amazon.com/redshift/latest/dg/r_SVV_ALL_TABLES.html), [columns](https://docs.aws.amazon.com/redshift/latest/dg/r_SVV_ALL_COLUMNS.html)

Record distribution/sort keys, compression, `SUPER` and external-table semantics in additional reviewed metadata. Declared keys do not replace independent uniqueness or fanout checks. Native EXPLAIN has statement-class limits, and physical design cannot be translated mechanically from Snowflake. [Table design](https://docs.aws.amazon.com/redshift/latest/dg/r_CREATE_TABLE_NEW.html), [constraint limits](https://docs.aws.amazon.com/redshift/latest/dg/t_Defining_constraints.html)

## ClickHouse

[clickhouse.sql](../examples/catalogue-queries/clickhouse.sql) reads connected-server `system.tables` and `system.columns`. Preserve endpoint/node/cluster scope, database/name, UUID where exposed, server version, native engine, full type/default expressions and key/partition expressions. The native namespace has two parts, database/table. In the canonical contract use catalog=database and schema=`__no_schema__`, explicitly recording that normalization; do not emit the marker as a native SQL qualifier. Engine names must remain distinct from normalized object types. [Tables](https://clickhouse.com/docs/reference/system-tables/tables), [columns](https://clickhouse.com/docs/reference/system-tables/columns)

A local server result does not inventory the whole cluster. Do not silently add `clusterAllReplicas`, widen grants, or flush logs. `ORDER BY`, primary keys, engines, materialized views, replication, TTL and mutations need separate interpretation and evidence. Optional definition exports may contain confidential paths/settings. Type wrappers such as Nullable/LowCardinality/Array require native type handling; do not infer nullability from a superficial string match.

## MotherDuck

[motherduck.sql](../examples/catalogue-queries/motherduck.sql) requires an already authorized explicit `md:` connection. It reads the selected attachment plus scoped Information Schema and optional view definitions. No extension installation, attachment creation, authentication or permission changes occur in these statements. Preserve remote organization/endpoint, authenticated cloud principal, attachment database/schema, DuckDB/client version and MotherDuck extension version separately. Local DuckDB `current_user` or a matching database alias is insufficient cloud-identity evidence. [MotherDuck connection](https://motherduck.com/glossary/motherduck/), [Information Schema](https://duckdb.org/docs/current/sql/meta/information_schema), [attachment/view metadata](https://duckdb.org/docs/lts/sql/meta/duckdb_table_functions)

An attachment can refer to local or remote data; retain its observed type and resolve it with trusted connection evidence. Do not collect every attached database by default. Client-version-specific fields and cloud capabilities need verification in the chosen environment. Local execution of these templates is simulation, not a MotherDuck catalogue qualification.
