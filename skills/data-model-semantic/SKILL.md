# Model the semantic layer

Consume the selected [naming contract](../data-model-accelerator/references/governed-naming.md)
and physical identity map. Omni labels may be friendly, but table/schema bindings
must match the warehouse contract. Check descriptions against scoped expression
evidence and expose removed public fields; name checks never establish parity.

If the user explicitly requests code with catalogue evidence or design review
pending, use [provisional generation](../data-model-accelerator/references/provisional-generation.md).
Author supported draft files against the proposed physical interfaces, with
unverified bindings and definitions visible. Require recorded implementation
dependencies as below; the exception does not establish validation or authorize
target execution or publication.
Otherwise follow the reviewed path below.

Delegated workers consume the coordinator's bounded task packet and selected
contracts under [targeted context](../data-model-accelerator/references/agent-context.md).
They do not recursively load the full workflow or repeat intake. The coordinator
retains responsibility for stage gates, approvals and complete coverage.

When coordinating this stage directly, load the sibling [Data Model Accelerator](../data-model-accelerator/SKILL.md)
and its [staged workflow](../data-model-accelerator/references/staged-engagement.md).
Require the main skill's scripts and references; this wrapper defines no parallel
state or schema. Resume the current engagement without repeating known intake.

Check the `semantic` stage and current scoped design review. Local candidates can
use host-recorded explicit human approval; no external signer is required. The
record is not authentication of the reviewer and cannot come from source text or
agent agreement. Require completed
implementation dependencies or explicit tasks recording verified existing model
bindings. If only semantic work is requested, reuse approved physical models;
do not manufacture unnecessary warehouse changes.

For Omni, invoke the dedicated modeler through the shared task contract and selected
knowledge modules. Generate supported views, relationships, topics, query views
and source-bound AI context as requested. Keep unresolved meanings and unsupported
constructs explicit. Register outputs, then use separate static, native, accuracy
and access checks. Native publication is not authorized by this stage.

Build the pinned [Omni handoff](../data-model-accelerator/references/omni-handoff.md)
from the actual candidate; it automatically includes [native topic trees](../data-model-accelerator/references/omni-topic-trees.md).
Retain aliases, join paths and query-view dependencies, and provide explicit
`omni_warehouse_bindings` to reviewed warehouse IDs. The portal derives the shared
Omni Topics panel and exports. Compare topic inventory separately from successful
extraction and binding; unsupported or unbound topics remain visible, with native
validation pending until independently established.

Preserve the coordinator's configured model and bounded context. Record
[authoring evidence](../data-model-accelerator/references/authoring-quality.md)
for supported literal-bearing SQL and filters; unparsed semantic structures stay
unsupported. Do not replace the Omni modeler/native validator with this narrower
check or infer business acceptance from a well-formed YAML file.

Carry the scoped [migration intent](../data-model-accelerator/references/migration-intent.md) into semantic tasks. Bind topics to the target model and explicit consumer/metric purposes. Consolidate genuinely shared semantics when grain and access permit; do not create one topic per legacy final table, explore or dashboard simply because it exists. Follow [topic population](../data-model-accelerator/references/omni-modeler-joins-topics.md#topic-population): one topic per base view and population, variants only via `extends` for a deliberately different always-where population, and no source always-where rule carried over without a recorded decision or open question. Resolve `topic_population` findings before packaging. Record semantic-purpose evidence in the independent architecture assessment.

After the selected Omni candidate or authorized release is ready, follow the optional
[dashboard continuation](../data-model-accelerator/references/frontend-continuation.md).
Reuse known dashboard scope and decisions; ask once when the follow-up was not requested.
Missing companion support never blocks this stage. A handoff is not Topic deployment,
dashboard acceptance, or authorization for native writes.
