# Capabilities and boundaries

Use this page to scope a customer pilot. The accelerator combines agent reasoning with deterministic local checks; it is not a universal parser, autonomous model compiler or preconfigured deployment service. Start with the [how-to guide](HOW_TO.md) and qualify one complete domain before expanding.

## Read capability claims correctly

[Design reliability](../skills/data-model-accelerator/references/design-reliability.md)
adds explicit multi-source coverage, independently captured reuse baselines,
provenance classes, canonical design assembly and scoped independent-review
records. The review page separates structural checks from coverage, human review
and native validation, and distinguishes models, sources and external interfaces.
These shared contracts apply to every supported target; hashes and host-reported
reviews do not establish warehouse truth or authenticated reviewer identity.
Older engagements remain compatible and report missing companions as unassessed.
Explicitly requested provisional code remains available when evidence is missing.

Optional [domain evidence and customer standards](../skills/data-model-accelerator/references/customer-modeling-standards.md)
preserve exact source identities, version imported classifications, and preview scoped
label, tag, description and sample-query requirements. They do not select domains,
rename physical models or grant approval. Unrelated rule changes preserve scoped work;
changed source evidence, naming policies or model identities expose stale context.

[Sensitive-field treatment](../skills/data-model-accelerator/references/sensitive-data.md)
separates source-qualified classification from destination-specific decisions. Masking,
tokenization and aggregation require explicit evidence; they do not automatically make
data non-sensitive. Unresolved treatment remains visible in provisional candidates;
native promotion has separate checks. [Scoped SQL contracts](../skills/data-model-accelerator/references/sql-contracts.md)
share the existing authoring receipt and exact-byte reuse checks. Unsupported SQL remains
unassessed, and static passes do not establish numerical parity or native security.

Topic consolidation recommendations compare effective filters and access boundaries.
Different audiences, grants or view-scoped definitions retain separate topics unless a
reviewed change explicitly resolves them. Changed definitions invalidate affected decisions.
The established small and partitioned guided pages remain the default; the alternative
[review presentation](../skills/data-model-accelerator/references/review-page.md) remains
available for further qualification rather than replacing existing delivery workflows. An optional
[domain review companion](../skills/data-model-accelerator/references/domain-review-page.md)
can be selected with `review.domain_review={"domain":"orders"}`. The existing finalizer adds
`03_Design_Documents/Domain_Review.html` (classic: `01_Model/Domain_Review.html`) when
documentation is selected and the review contains models. The standard `START_HERE.html`, audience, selected
files, disclosure checks and provisional status remain authoritative. The companion preserves
selected dbt, native SQL or Coalesce paths and uses explicit warehouse bindings for Omni;
missing evidence stays unassessed. Its standalone draft/promotion tools support internal
review versioning, not completed delivery, native validation or authorization.

[Migration intent](../skills/data-model-accelerator/references/migration-intent.md)
separates preserved business semantics from requested structural change. Scoped
repository roles, evidence-bearing specialist briefs and current objective
assessments prevent file coverage from silently becoming a refactor claim.
Bounded legacy-copy/wrapper observations expose retained implementation; they do
not establish semantic equivalence or guarantee detection of all wrappers.
Provisional generation and older engagements remain supported.

Optional [migration planning](../skills/data-model-accelerator/references/migration-planning.md)
turns retained, domain-scoped design and historical alignment into an editable
Excel inventory, Word migration plan, and ticket templates/import candidates.
The focused project-manager role records consumer destinations, dependencies,
acceptance criteria, waves, unknowns and effort categories without rescanning the
source repository. Stable item IDs preserve human edits across revisions.
Google formats produce typed content for native host creation; they remain
pending until creation and read-back are confirmed. Import candidates require
the selected system's field mapping and review. These capabilities do not post
tickets, verify live importer compatibility, establish parity or authorize a release.

Optional [historical table alignment](../skills/data-model-accelerator/references/legacy-alignment.md)
adds per-domain new/refactor/mixed intake and a retained predesign baseline.
It supports many-to-many table/column/rule mappings, target semantic placements,
explicit missing coverage, scoped human decisions and incremental freshness.
The guided review and selected CSV/Markdown documentation share one comparison.
Existing reuse contracts and engagements without this option retain their behavior.
Bounded local context preparation and validation-case suggestions do not execute
an agent, infer undocumented spreadsheet formulas, prove data parity, or authorize
publication. Platform support follows the existing parsers and emitters; this
feature does not add new warehouse execution adapters or native validation.

The optional [migration review workflow](../skills/data-model-accelerator/references/migration-review.md)
connects four local capabilities: a reusable scoped business-rule register with
explicit human decisions; actual Periscope/CDT Git discovery and extraction with
version/coverage records; deterministic shared-model recommendations across
dashboard contracts; and a private export-to-scorecard comparison from source to
warehouse to Omni. The guided page and selected documentation include the results.
Changed inputs invalidate affected evidence. Matching declared contracts is a
candidate recommendation, not proof of equivalence; comparison passes establish
local consistency only. Bounded signed BigQuery/Omni collectors have synthetic
contract tests and remain live-unqualified. No new feature authorizes deployment
or removes requested provisional code generation.

| Level | What it means |
| --- | --- |
| Discovery / routing | Recognizes bounded evidence and selects a specialist; does not prove complete parsing or lineage |
| Agent-assisted generation | Guides an agent to author a candidate from inspected evidence; does not deterministically translate arbitrary projects |
| Contract-tested | Local fixtures exercise request, validation, state or receipt behavior |
| Locally executed | A named fixture or candidate actually ran in its recorded local runtime |
| Native-qualified | The exact project ran in the selected service with identity, permissions and independent acceptance evidence |

The repository includes the first four levels for different surfaces. **No warehouse or BI platform has blanket native qualification.** A passing example is evidence for that example and version. For exact results, read the [qualification ledger](qualification.md).

## dbt runtimes and upgrades

For dbt, the [runtime workflow](../skills/data-model-accelerator/references/dbt-runtime.md)
keeps existing Core requests compatible while adding explicit full dbt v2 and
dbt OSS selection, a read-only upgrade assessment, bounded Information Schema
ingestion, optional metadata-check candidates and separate native lint evidence.
The guided package includes runtime/setup context; changed runtime choices
invalidate affected code and checks without discarding the reviewed design.
Feature availability and warehouse support do not imply native qualification.

## Warehouse metadata delivery

The shared v2 dictionary records approved descriptions, grain, units, classification, multiple key roles, exact source lineage and unresolved decisions. The dbt generator previews and safely merges owned YAML fields into a separate candidate, preserves human changes and sets `persist_docs` with explicit override reporting. Native planners generate bounded comments for all six warehouses, with informational custom tags for Snowflake and Unity Catalog where supported. Unsupported security/tag semantics stay in the dictionary or block the selected write.

Independent metadata exports are reconciled against the full physical scope, then against expected comments and direct tag assignments. The guided Metadata page and ZIP retain the plan, exclusions, changes and evidence associations. Downstream handoff preserves the same definitions and physical names for Omni/AI review. Local signed simulations exercise linked build/metadata phases, wrong destinations, immutable expected scope, partial failure, recovery locks and independent acceptance.

**Remaining boundaries:** automatic live metadata dispatch is blocked pending an authenticated current-state collector. Reviewed SQL/operator or independently governed CI delivery is available. Governance provisioning, policy changes, native Coalesce node projection, live provider qualification and actual Omni refresh remain separate work. Local DuckDB persistence is not MotherDuck execution. Read the [metadata guide](../skills/data-model-accelerator/references/warehouse-metadata.md) and [qualification and reproduction](qualification.md).

## End-to-end workflow

Explicit [provisional code requests](../skills/data-model-accelerator/references/provisional-generation.md)
permit supported warehouse and semantic draft files while catalogue evidence or
design review is pending. Requested stage/entity coverage stays visible; design
documents do not satisfy a code request. This does not create approval, verified
bindings or execution authority. Changed evidence requires reconciliation, and
unknowns remain placeholders or gaps.

## Omni and AI context

The tested source-only candidate contains native `.view`, `.topic`, `model` and `relationships` files, with separate facts/topics for different grains. Its local validation covers field bindings, join roles, measure inputs, dimensions, grouped results and supported expressions. Environment placeholders are packaging tokens that must be resolved before import.

AI context records topic purpose, grain, formulas, date roles, known ambiguity, publication exclusions, supported questions and when to request clarification. With SMEs available, accepted definitions can replace provisional interpretations and trigger affected tests. Context must never present an inferred definition as accepted simply because a query runs.

The latest trial generated nine views, three topics and 15 measures. Local replay covered 52 measure cases, 11 join roles, 99 dimensions and eight grouped queries. **Native Omni import/query execution and live AI-answer accuracy remain unqualified.** The local interpreter supports a bounded subset; unsupported expressions are gaps. AI guidance, hidden fields and topic curation do not replace effective access controls.

## Four independent validation lanes

| Lane | Examples | A pass does not establish |
| --- | --- | --- |
| Code conventions | SQLFluff dialect, structured native files, file/unit inventory, hashes, disclosed exceptions | Correct business results, native execution or security |
| Project validity | Selected framework structure, compilation, complete associated build results | Source fidelity or business approval |
| Warehouse validity | Actual target identity, object/type resolution, eligible statement planning and native execution | Full workload behavior or approved definitions |
| Data and semantic accuracy | Frozen row/key/value expectations, fanout, orphan populations, date roles, precision, access personas and semantic queries | Untested scenarios or universal hallucination prevention |

The lint runner checks all rules and rejects missing inventory, unresolved templates, suppression directives, malformed structured files and runtime failures. Narrow exact-file style exceptions require a rule, reason and bound content hash; raw findings remain visible and unused/forged exceptions fail. Parser, coverage and data failures cannot be waived through that mechanism. [Lint contract](../skills/data-model-accelerator/references/linting.md)

Actual execution and deliberate defect tests are essential. A row-count check can miss the wrong date-role join; a passing dbt uniqueness test can miss the wrong amount. A native permissions test needs known allowed and denied personas. State/history requires multiple runs, corrections, deletes and recovery cases.

## Deployment capability

The coordinator has contract-tested routes for existing GitHub workflows, dbt hosted jobs, Coalesce, Snowflake SQL, Databricks bundles/jobs, BigQuery SQL, Dataform, Redshift SQL, ClickHouse SQL and MotherDuck SQL. Each has its own request, result and recovery limits. No native provider deployment has been qualified by these fixtures.

Direct Coalesce live submission is blocked before mutation because its automatic status/results commands use profile-resolved domains that this runner cannot bind to the approved destination. Explicit cancellation pins its documented destination flags. A qualified existing CI/operator workflow remains the handoff path; the current Coalesce route cannot claim automated verified completion. This is a known implementation limit in addition to native qualification requirements.

PR publication is separate: it creates a draft PR for a reviewed branch already present remotely, verifies its identity and files, and does not commit, push or merge. The host can separately perform explicitly requested Git work through the customer's normal release process. Publishing this accelerator repository does not deploy a customer model.

The guided page can export a deployment request after review. It cannot manufacture human sign-off or provision credentials. Live use requires trusted destination policy, external approval/validation issuers, target preflight and an exact version. Native completion initially awaits independent acceptance. Ambiguous outcomes remain uncertain rather than being blindly resubmitted. [Runner and route details](DEPLOYMENT.md)

## Minimum evidence for the first customer pilot

- One selected domain, its source repository/dependencies, and identified downstream outputs.
- A scoped, current raw catalogue and authorized profiling or representative data access.
- An engineer responsible for the patch and SMEs able to resolve the relevant definitions.
- Independent expectations for the selected outputs; preserve existing behavior and approved corrections separately.
- A development target and explicit allowed/denied access personas for native testing.
- A reviewed deployment/cutover path, recovery evidence and an identified acceptance owner before promotion.

Without SMEs, the accelerator can still deliver a structural proposal and source-derived comparisons with unknowns retained. With SMEs, it can resolve meaning through a focused decision loop. Neither scenario justifies an overall “80–90% accurate” claim without a defined denominator and customer-specific measurements.

## Agent hosts

The skill is intended to travel as a complete folder across capable coding-agent hosts. The [host guide](../skills/data-model-accelerator/references/targets-and-hosts.md) documents Codex, Claude Code, Gemini CLI, Cortex Code and Genie Code setup considerations. Current development evidence comes from Codex. Equivalent end-to-end runs on the other hosts, Cortex Agents packaging, and every host's delegation/execution surface remain separately unqualified.

### First-use model review

The shared offline handoff includes a searchable table navigator, fit/actual-size/expanded ERD, responsive table inspector, exact table-to-code links, scope-specific evidence detail and version-bound feedback requests. Selected model projections also ship as standalone SVG/editable source and CSV/Markdown dictionaries. The manifest distinguishes these generated presentation files from registered artifacts; smaller browser exports retain artifact integrity and explicitly require a fresh disclosure review. Legacy packages remain readable. These are review/packaging capabilities across the existing platform routes, not added warehouse execution or native validation support.

### Sequential domain delivery

- Discover candidate domains once; require a user choice before detailed design.
- Review, approve and generate one domain's selected code before offering the next.
- Track queued, active, paused, completed and stale domains in the guided review.
- Preserve shared model identities and completed task reuse; recheck affected scopes
  after input or output changes.
- Keep explicitly requested provisional code and legacy engagements available.
- Completion is reviewed candidate code, distinct from native validation, final
  packaging, business acceptance and deployment authorization.
